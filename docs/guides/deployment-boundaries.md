# 部署与请求重试边界

## 单进程部署与请求重试边界

Mako 当前支持一个 API 进程、一个应用实例。Docker 镜像固定 `--workers 1`；直接运行时使用：

```bash
python -m uvicorn api.main:app --host 127.0.0.1 --port 8000 --workers 1
```

不要增加 Uvicorn/Gunicorn worker 或在负载均衡后启动多个 Mako 副本。`/chat`、`/v2/workspace/analyze`、`/v2/workspace/analyze/files` 的请求缓存及工作区会话均位于进程内；已有 Redis 工作记忆不等于这些缓存已共享。不同进程可能各执行一次同键请求，或不认识另一个进程发出的工作区会话。

请求复用范围：

- 同一进程内，键和请求内容一致时可复用进行中的任务或已返回结果；不同内容使用同键会报冲突。
- 缓存从首次创建任务起保留五分钟；超时仍在执行的请求也不享有跨缓存窗口保证。
- 执行失败后缓存会清除，重试可能再次调用模型；服务重启也会丢失缓存。它不是永久的“只执行一次”承诺。
- 任务/材料创建使用的 SQLite 幂等记录另有持久化边界，不能据此推断模型请求或工作区会话支持多实例。

启动日志会说明上述限制，并尽力识别 `WEB_CONCURRENCY`、`UVICORN_WORKERS` 和命令行 `--workers` / `-w` 的不支持设置。显式命令行参数优先。程序化创建的 worker 和其他主机上的副本无法靠本进程完整识别；没有告警不代表拓扑受支持。

若未来要扩展多进程或多实例，需要先实现共享的请求指纹、执行归属、结果与会话协调，并验证故障接管和重试行为。当前没有加入这类分布式能力。
